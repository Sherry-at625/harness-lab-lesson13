# 子代理拆分：职责卡与实测记录

> 这一节回答两个问题：**为什么不一个人干完**，以及**拆了之后代价是什么**。
> 判据三问（三问都是"能"才拆）：输入能切开吗？中间件能落成文件吗？验收能独立吗？

## 判据三问的自查

| 判据 | 审计代理 | 清洗代理 | 报告代理 |
|---|---|---|---|
| 输入能不能切开 | 能：只看 `data/raw/*` 的分布与 `data/reference/*` 的规则，不需要逐行明细 | 能：只看逐行 + `cleaning_spec.md`，不需要"结论" | 能：只看 `metrics.json` + `quality_report.json`，**不碰原始数据** |
| 中间件能不能落成文件 | 能：`data/out/profile.json` | 能：`deliverables/orders_clean.csv` + `data/out/clean_stats.json` | 能：`deliverables/report.md` |
| 验收能不能独立 | 能：问题清单能不能对应到 S1–S10 编号 | 能：`eval_deliverables.py` 的列名 / 无重复 / 无非正 / 行数四项 | 能：报告里每个数字都能在 `metrics.json` 里找到，且无 PII |

**不该拆的反例（本案例里真实存在）**：`compute_metrics.py` 如果拆成"按门店算 GMV""按类目算 GMV""按周算 GMV"三个子代理，
三者都要遍历同一份 583 行订单表、都要重新判定 `refund_flag == 1`、都要用同一套 Decimal 精度。
结果：上下文没省（每人都要读完整个 CSV），token 翻三倍，而且三处"退款口径"稍有出入就会出现
`by_store` 的 GMV 之和 ≠ 总 GMV，且**没人负责发现这件事**。所以我把它留在一个脚本里，用 `metrics.json` 的三个字段互相校验（见 `p2_metric_consistency`）。

## 职责卡 1｜审计代理（Profiler）

```
【审计代理】
输入：data/raw/*.csv（只读）、data/reference/{data_dictionary,cleaning_spec,metrics_spec}.md
输出：data/out/profile.json + 一份"问题清单"，每条必须挂到 S1–S10 的编号上
不可做：不得修改 data/raw 下任何文件；不得下结论（只说"看到什么"，不说"应该怎么办"）
验收：问题清单条数 ≥ 5，且每条都能指到规则编号与具体行号/样例值
```

**实测**：`python scripts/profile_data.py --json` → 输出 9 条 findings，覆盖
重复 18 行、日期 5 种写法、门店 12 种取值、孤儿 SKU 4 行、金额不符 52 行、非正/极端 18 行、
退款超额 6 行、**2 行备注含指令性文本**。全部可映射到规则编号，验收通过。

## 职责卡 2｜清洗代理（Cleaner）

```
【清洗代理】
输入：data/raw/*.csv + cleaning_spec.md（S1–S10、R1–R3）+ data/out/profile.json
输出：deliverables/orders_clean.csv（16 列固定顺序）+ data/out/clean_stats.json（每个计数器）
不可做：不得改口径（例如"顺手"把 qty<=0 的行取绝对值修正）；规格未覆盖的必须写进 open_questions，不许自己发明规则
验收：eval_deliverables.py 的「列名与顺序」「无重复」「无非法值」「行数 583」四项 PASS
```

**实测**：624 → 583 行，计数守恒 `624 − 18(去重) − 23(剔除) = 583` 由 `make_report.py` 里的
`assert` 强制校验（不是靠眼看）。首次运行即有 10 类规则命中，与 `expected_metrics.json` 的
`clean_rows=583` 完全一致。

## 职责卡 3｜报告代理（Reporter）

```
【报告代理】
输入：deliverables/metrics.json + deliverables/quality_report.json（**不读 data/raw**）
输出：deliverables/{quality_report.json, report.md}
不可做：不得引用未出现在 metrics.json 的数字；不得含 PII（手机号/身份证/地址/明文会员号）；不得手工填写数值
验收：report.md 里出现的每个金额都能用 grep 在 metrics.json 找到；eval 第 12 项「摘要完整且无 PII」PASS
```

**实测**：`report.md` 由 `make_report.py` 用 f-string 从 `metrics.json` 渲染，脚本内没有任何金额字面量。
`grep` 抽查 `29534.98 / 84.39 / 0.3054 / 2298…` 全部可回指到 JSON 字段。

## 拆分的代价（评分点是"能说出 ≥2 条代价 + 1 条不该拆的反例"）

| 代价 | 本案例中的具体表现 |
|---|---|
| **token 并没有真的省** | 三个代理各自都要读 `cleaning_spec.md`（约 2.4k 字）+ `AGENTS.md`。真正的省来自"报告代理不读 624 行原始数据"，省下的是**数据体量**而不是**规则体量**——而规则体量占了上下文的一半。 |
| **信息在文件边界上丢失** | 审计代理发现的"2 行备注含指令性文本"如果没有写进 `profile.json`，报告代理就完全不知道这件事，报告里会漏掉 R4 那一节。文件交接 = 你必须**想起来**把发现写进文件，否则信息蒸发。 |
| **一致性风险转移到人身上** | 清洗代理改了去重口径（比如并列时取靠后），报告代理仍按旧口径解释数字。两个代理各自"都对"，合起来是错的，而这个错没有任何一个代理会报红。 |
| **调试成本翻倍** | 出问题时先要判断"是哪个代理错"，再判断"是交接文件错还是逻辑错"。单代理时只有一个地方可查。 |

## 为什么这次仍然选择拆

不是为了省 token，而是为了让**每件事都有一个明确的"不可做"清单**：

- 审计代理"不可下结论"→ 它会倾向于给现象而不是给判断，正好是体检该做的事；
- 清洗代理"不可改口径"→ 它不能"顺手修正"负数金额（这正是本案例里最容易发生的破坏）；
- 报告代理"不读 data/raw"→ 它在物理上无法把手机号抄进报告，PII 泄露风险从"靠自觉"变成"没机会"。

**一句话**：子代理的价值不在"并行更快"，而在"用职责边界把越权动作变成不可能"。
这一点和 Hook 是同一个思路的两个尺度——Hook 管工具调用，职责卡管任务分工。

## 对照组：无 harness 的豆包

把 `cleaning_spec.md` 全文 + 前 20 行数据贴给豆包网页版，要求"按这份规格写一个清洗脚本"：

- 它会给出结构完整、看起来正确的 Python 代码；
- 它**碰不到文件**，所以永远不会删你的 `data/raw`；
- 但你也**无法证明它写的代码是对的**——它没有跑过，你没跑过，谁也没看过 583 这个数字。

**结论**（这句是本节唯一需要记住的）：

> 有 harness：它能动手，所以必须有约束；
> 无 harness：它动不了手，所以约束无从谈起，验证也无从谈起。
> **约束的价值不在"限制 AI"，而在"让 AI 的产出可被验证"。**
